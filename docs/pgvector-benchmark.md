# pgvector 基准测试

## 测试目的

本测试比较 JSON 向量 + Python 全量扫描、pgvector 精确检索和 HNSW 近似检索。结果用于选择读取策略，不用于宣称通用硬件性能。

## 环境与口径

- PostgreSQL 16，pgvector 0.8.1。
- 单机 Docker 开发环境，数据为可复现的合成向量。
- 规模为 10k、50k、100k ParagraphEmbedding。
- 质量以 HNSW Top-10 对同库精确 Top-10 的 Recall@10 计算。
- 延迟是该环境下有限查询样本的 P50；不等同于生产并发容量。

## 结果摘要

| 数据量 | HNSW 参数 | Legacy P50 | Exact P50 | HNSW P50 | Recall@10 |
| ---: | --- | ---: | ---: | ---: | ---: |
| 10k | m=16, efc=64, efs=100 | 671.84 ms | 26.95 ms | 21.87 ms | 0.890 |
| 50k | m=32, efc=200, efs=200 | 2572.68 ms | 37.66 ms | 26.76 ms | 0.960 |
| 100k | m=32, efc=200, efs=200 | 5711.87 ms | 53.48 ms | 46.88 ms | 0.925 |
| 100k | m=32, efc=200, efs=400 | — | 43.39 ms | 55.25 ms | 0.945 |
| 100k | m=32, efc=200, efs=600 | — | 45.30 ms | 72.31 ms | 0.970 |

50k 重建索引后的大小约 78 MB；10k 默认参数索引约 13 MB。不同运行之间 Exact 延迟存在缓存和系统负载波动，因此比较时需查看完整逐查询记录。

## 结论

数据库内精确检索相较 Python 全量扫描有数量级改善。HNSW 在 50k、Recall@10 0.96 的条件下同时改善延迟；在 100k 环境中，提高 `ef_search` 才能达到 0.97，但 HNSW 已慢于精确检索。因此当前硬件和数据规模下不应强制启用 HNSW，应按空间和规模设置质量门槛，并保留 Exact 与 Legacy 回滚路径。

原始 CSV/JSON 结果保存在 `evals/results/`。这些数字只描述本次合成数据实验；上线前仍需使用真实冻结集和生产相似硬件完成 Shadow 验证。

## 复现

使用管理命令创建受保护的基准知识库与向量，分别执行 Legacy、Exact 和 HNSW 查询。命令只允许清理带固定测试前缀的数据；执行前仍需确认数据库为测试环境。索引参数、查询次数、随机种子和结果文件应随报告保存。
