# pgvector 向量存储与迁移

## 目标

旧实现把向量保存为 JSON，并由 Python 拉取全部候选后计算余弦相似度。该方式便于本地启动，但计算和传输成本随切片数量线性增长。生产路径使用 PostgreSQL 与 pgvector，把空间过滤、距离计算、排序和 Top-K 截断下推到数据库。

## 数据模型

- `EmbeddingSpace` 描述 owner、模型配置、revision、维度和距离度量形成的向量空间。
- `ParagraphEmbedding` 保存 Paragraph 在特定空间中的向量，并冗余知识库外键用于安全过滤和索引查询。
- `VectorMigrationRun` 记录回填游标、状态、计数和错误摘要，支持中断恢复和审计。

Paragraph 与 EmbeddingSpace 之间具有唯一约束，避免同一切片在同一空间重复写入。知识库、空间和配置的 owner 必须一致。

## 读写策略

文档上传和重处理通过统一存储服务写入向量。迁移期支持：

- Legacy：只使用原 JSON 路径。
- Dual write：写入 JSON 的同时写 pgvector，失败按策略记录并降级。
- Shadow read：主请求沿用当前结果，后台比较 pgvector 排名和耗时。
- pgvector read：通过数据库运算符完成精确或 HNSW 检索。

切换读取路径前必须完成回填、完整性核对、真实冻结集质量比较和回滚演练。Legacy 字段不会因一次成功基准测试而立即删除。

## 查询约束

每次查询必须同时限定：

1. 当前用户或组织可访问的知识库。
2. 当前知识库绑定的 EmbeddingSpace。
3. 文档处理成功且 embedding signature 匹配。
4. 需要的 Top-K 和距离阈值。

这些条件在数据库查询中生效，不能在取回全表后再由 Python 过滤。查询向量维度与空间不一致时返回明确错误，禁止以零分静默吞掉问题。

## HNSW 索引

HNSW 是近似检索，参数需要按数据量、维度、硬件和质量门槛校准：

- `m` 与 `ef_construction` 影响构建时间、索引大小和图质量。
- `ef_search` 影响查询召回与延迟。
- 数据量较小时，精确检索可能比满足高召回门槛的 HNSW 更快。

因此索引启用由实测决定，而不是默认宣称 HNSW 一定更优。管理命令提供创建、重建、检查和删除能力；生产操作需在低峰执行并观察锁、磁盘和查询延迟。

## 回填与回滚

回填使用稳定主键游标分批读取，任务具有幂等性，可由 Celery 调度并通过 Redis 锁避免同一空间并发执行。每批提交后更新游标；重试不会覆盖其他空间或产生重复记录。

回滚只需把读取模式切回 Legacy；双写可继续保留用于排查。只有在观察期通过且备份可恢复后，才评估清理旧字段。实测结果见 [pgvector 基准测试](pgvector-benchmark.md)。
